## Cron / scheduler state

**Status: PARTIALLY wired — one real schedule exists; two classes are missing.**
AUDIT.md risk #17 ("No schedule in repo") is **out of date.**

### What IS scheduled today

[supabase/migrations/20260511170000_reconciliation_engine.sql:159-172](supabase/migrations/20260511170000_reconciliation_engine.sql:159):
```sql
CREATE EXTENSION IF NOT EXISTS pg_cron;
-- (unschedule-if-exists guard)
SELECT cron.schedule(
  'zuri_hourly_reconciliation',
  '0 * * * *',
  $$ SELECT public.run_reconciliation('scheduled'); $$
);
```
This runs the **ledger reconciliation** (`run_reconciliation`) **every hour** —
orphan-debit/credit detection, balance-mismatch detection, hash-chain validation,
writing a row to `reconciliation_runs`. This is real and live (assuming `pg_cron`
is enabled on the Supabase project — see Risks).

### What is NOT scheduled (the gaps)

1. **Stuck-payment Daraja STK-Query sweep.** The `reconciliation-job` **Edge
   Function** (which queries Daraja for `waiting_for_mpesa` rows older than the
   threshold and resolves timeouts) is **only triggered on-demand** from the
   admin UI / manual RPC. `run_reconciliation` (the pg_cron job) does **ledger**
   recon, not Daraja STK-Query. AUDIT.md §21 ("Reconciliation cadence — On-demand
   today … Cron every 5 min on 7-day plan") still stands for *this* sweep.
   - **Why it can't just be another `cron.schedule`:** pg_cron runs SQL inside
     Postgres; calling an Edge Function needs `pg_net`/`http` (an outbound HTTP
     POST to the function URL with a service header) or an external scheduler.
     This is a small but real piece of infra to add.
2. **Stale-row cleanup helpers — defined but NOT scheduled.** Three cleanup
   functions exist as helpers with comments saying they *can* be scheduled, but
   no `cron.schedule` calls them:
   - `cleanup_expired_webauthn_challenges` — "called by the edge function and can
     be scheduled via pg_cron" (`20260517000001_webauthn_credentials.sql:55`).
   - stale-OTP cleanup — "Safe to schedule via pg_cron"
     (`20260519020000_otp_records_hardening.sql:144,180`).
   - `cleanup_expired_idempotency_keys` — `20260511120000_idempotency_keys.sql:41`.
3. **Notification queue drainer** — does not exist yet (see STUB `notifications`);
   once 6.2 ships a worker, it needs a schedule too.

**Implication:** Phase 6 cron work = (a) add `pg_net`/http-based schedules (or a
Supabase scheduled-function) for `reconciliation-job`, the notification worker,
and the three cleanup helpers; (b) confirm `pg_cron` is actually enabled in the
target project.

## Risks identified (things that would surprise us in 6.2–6.8)

1. **`pg_cron` enablement is a project setting, not just a migration.** The
   migration does `CREATE EXTENSION IF NOT EXISTS pg_cron`, but on Supabase
   `pg_cron` must be enabled for the project's database (Dashboard → Database →
   Extensions) and only runs in the `postgres` database. If it isn't enabled on
   the target project, the hourly reconciliation is **silently not running** and
   any new schedules will fail. **Verify `cron.job` actually has rows before
   trusting any "it's scheduled" claim.**
2. **Calling Edge Functions from cron needs `pg_net`/`http`.** Scheduling
   `reconciliation-job` / the notification worker isn't a one-line `cron.schedule`
   — it needs an HTTP egress mechanism (pg_net) plus a way to authenticate the
   call (service header / shared secret). Plan a small migration + secret for this.
3. **`notifications` table is under-specified for a worker.** Current columns are
   just `user_id, channel, body, status`. A real worker needs `attempts`,
   `last_error`, `next_attempt_at`, `delivered_at`, a `provider_message_id`, and a
   dead-letter terminal status — i.e. a migration **before** the worker.
4. **Two "phantom read" tables make risk/telemetry look richer than it is.**
   `risk_events` and `device_sessions` are read by the risk engine but never
   written, so those signals are always empty. If Phase 6 monitoring surfaces
   "device recognized" or "prior risk score" metrics, they'll read zero. Decide
   to backfill or drop.
5. **Notification double-meaning.** There are *two* notification systems: the
   `notification-dispatcher` Edge Function (enqueue-only) and the client-side
   `src/lib/notifications.js` + `src/api/notifications.js` simulation. The
   front-end currently calls the **fake** local one (`NotifLib.sendNotification`),
   not the Edge Function. 6.2 must also **rewire the client** to the real worker
   path, or receipts/alerts will keep going to `sessionStorage` and vanish.
6. **No alerting sink exists.** There is no Slack/Discord/PagerDuty webhook URL or
   email transport anywhere in the repo. The OPS_RUNBOOK escalation table is
   `_TBD_`. Alerting (6.6) is blocked until a destination secret exists.
7. **AT integration is OTP-shaped, not generic.** The shared helper hardcodes the
   OTP-style success-code set and message handling around AT *SMS*. Reusing it for
   transactional notifications is easy, but **push (FCM) and email are not present
   at all** — if those channels are in 6.2 scope, they're new integrations.
8. **`settlement-recovery` Edge Function exists but was not in any write/read path
   surfaced here** — worth a one-line confirmation during 6.x that it's still
   wired to something (it appears in the AUDIT staging checklist but no table
   write was observed in this sweep).
