### `src/App.jsx` — **LIVE — BLOCKER**

The app shell imports `startRuntimeHealthMonitor` and `startStartupWatchdog` from `@/backend/observability`. Both run in a `useEffect` on every authenticated page load:

**Panels/sections affected:** No UI panel — these run silently in the background. Removing them requires either (a) deleting the calls, or (b) wiring them to a real `/health` Edge Function. Per AUDIT.md §17, the latter is the correct fix.

## Recommended role model

### Four-role model (recommended for post-launch)

| Role | Access | Can trigger actions? | PII access? |
|---|---|---|---|
| `admin` | All 12 panels + all admin Edge Functions | Yes — can trigger reconciliation, revoke devices, verify/reject providers, approve reversals | Full |
| `auditor` | All 12 panels, read-only; no action buttons rendered | No | Full (PII read-only for regulatory evidence) |
| `fraud_analyst` | Panels 3, 5, 7 (audit stream filtered to fraud/security), 12 (wrong-number reports); no Device Trust, no Manual Review payment details | Can flag wrong-number reports; cannot reverse, cannot change permissions | No PII — sees tx refs and risk reasons, not phone numbers or balances |
| `operator` | Panels 1, 2, 4, 8, 10, 11; no risk trend details, no audit stream, no device trust | Can re-trigger reconciliation jobs and mark manual-review items resolved | No PII |

### Minimum viable for solo launch: `admin` + `auditor`

The four-role model is correct for a team with 3–8 ops staff but over-engineered for a single-operator launch. For the Safaricom pitch, launch with `admin` + `auditor`. Plan the four-role model for the first post-launch sprint. The RLS and `app_metadata.role` schema already support arbitrary role strings, so adding `fraud_analyst` and `operator` is additive — no migration needed.

**Do NOT invent a fifth role.** `operator` vs `auditor` is the critical distinction: one reads, one acts. Every fintech that conflates them eventually has an auditor accidentally trigger a reconciliation run.

## Risks identified during audit

### R1 — `src/lib/riskEngine.js` shadow call is on the LIVE payment path (HIGH)
Every Send/Airtime/Bundles/Paybill transaction runs `evaluateAdaptiveFraudEscalation`, which reads and writes to localStorage. The risk score it produces is **additive** on top of the server's risk decision, not a replacement — so deleting it may (correctly) reduce a falsely-elevated client-side score. Verify that the server-authoritative risk decision covers the same signals before removing the client layer. Specifically confirm that `required_step_up` is always returned from `risk-engine` Edge Function when a step-up is warranted.

### R2 — `src/App.jsx` health monitor is always-on, not gated (MEDIUM)
`startRuntimeHealthMonitor` runs a 30-second polling loop that reads localStorage on every page for every authenticated user. This is silent dead weight post-deletion. The stub functions currently return gracefully if their data is missing, but deleting the module without removing the calls first will throw a module-not-found error at build time.

### R3 — `src/backend/webhooks/verifyWebhook.js` is pure-function crypto — do not delete before confirming Edge Function parity (LOW)
`verifyWebhook.js` implements HMAC-SHA256 with timing-safe comparison, clock-skew tolerance, and payload-size limits. The real webhook-handler Edge Function should have equivalent logic. Before Stage C of 5.6, compare `verifyWebhook.js` against `supabase/functions/webhook-handler/index.ts` to ensure no logic gap. If the Edge Function is missing any of these checks, lift them to the Edge Function first.

### R4 — `src/backend/policy/` is 2,281 lines with zero live importers — safe but misleading (LOW)
The policy engine is well-architected and was never wired into a live flow. Its schemas (policySchemas.js) define TypeScript-style JSDoc types that are not used in any TypeScript file. Deletion will not break the type checker because these are JSDoc-only types in plain JS files, not actual `.d.ts` exports.

### R5 — No database tables exist solely to support shadow code (CONFIRMED SAFE)
All tables found in migrations (`webhook_events`, `webhook_nonces`, `audit_events`, `risk_decisions`, etc.) are used by real Edge Functions. The shadow stack **reads from localStorage**, not from these tables. No migration drop is needed as part of Phase 5.

### R6 — `tests/unit/reconciliation.test.js` mixes shadow and real interfaces (LOW)
The test imports `replayLedger` from the shadow stack but mocks `@/services/ledgerService.js` and `@/services/reconciliationService.js` (which are real service wrappers). This is a mixed test: it tests shadow logic against mocked real-service interfaces. The test should be rewritten in Phase 5.5 to test the real reconciliation RPCs against the database, or deleted if the function is not exported from the real stack.
