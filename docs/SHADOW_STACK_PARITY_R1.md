**How the return value is consumed in `riskEngine.js`:**


Only three numeric bumps and a set of reason strings flow out into the client risk
score. No return value is sent to the server — this is purely a client-side

## Verdict

**SAFE TO REMOVE**

The server-side risk engine covers all meaningful signals via real database queries
and makes the authoritative `allow / step_up / block / manual_review` decision.
The shadow code's two localStorage-backed signals are **dead in production**:

- `zuri_reputation_v1` is only written by `recordFraudGraphEvent` in
  `src/api/payments.js`, which has zero importers (confirmed orphan module, to be
  deleted in Phase 5.6 Stage A). localStorage store is always empty.

- `zuri_shared_threat_intel_v1` is only written by `recordThreatSignal`, which
  Part B.3 stubs as a no-op. Even before this stub, the function was never called
  from the production payment flow. localStorage store is always empty.

Removing `evaluateAdaptiveFraudEscalation` will reduce a localStorage-polling
overlay that contributes **zero real signal** in production. The only non-zero
client contribution today is `deviceRisk.fraudSensitivityBump` (from
`@/lib/deviceTrust`, not the shadow stack), but the server already enforces device
trust via the `device_sessions` table and `trusted_devices` deny-list with
hard-denial semantics that are stronger than a score bump.

The `required_step_up` in the server response has always been the authoritative
gate. Removing the client overlay does not regress that gate.
